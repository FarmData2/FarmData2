## 12. Mark your pull request as ready for review.

<!-- eslint enable no-heading-punctuation -->
<!-- vale RedHat.HeadingPunctuation = YES -->
<!-- vale Google.HeadingPunctuation = YES -->
<!-- vale Microsoft.HeadingPunctuation = YES -->

When you feel that the proposed changes in your pull request are complete, mark your pull request as [Ready for review](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/changing-the-stage-of-a-pull-request). Marking your pull request as ready for review signals to the maintainers that you believe that your changes are polished, tested and ready for them to review in detail.

When you mark a pull request as ready for review, all commits in the pull request will be processed as follows:

- Each unique `Assisted-by` commit trailers will be added to the "Attributions" section of the pull request body.
- The `Generated-by` trailers in all commits will be processed as follows:
  - If all commits in the pull request have a `Generated-by` trailer, each unique trailer will be added to the "Attributions" section.
  - If there are commits with `Co-authored-by`, `Assisted-by` or no trailers, then each unique `Generated-by` trailer will be added to the "Attributions" section as an `Assisted-by` trailer.
- A [series of status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks) is run. These status checks require that:

  - The licensing certification checkbox has been checked.
  - All placeholder information has been removed from the pull request description.
  - The pull request description does not contain any empty sections.

  If any of these status checks fail, the pull request will be converted back to a draft and information about the failures will appear near the bottom of the pull request page. Review the status check details, correct any issues and mark your pull request ready for review again.
