## 7. Commit changes to your feature branch.

<!-- eslint enable no-heading-punctuation -->
<!-- vale RedHat.HeadingPunctuation = YES -->
<!-- vale Google.HeadingPunctuation = YES -->
<!-- vale Microsoft.HeadingPunctuation = YES -->

Each time you complete a _nameable unit of work_, commit the changes to your feature branch. Committing _nameable units of work_ and using meaningful commit messages will be helpful in identifying earlier commits if you need to revert to an earlier state.

One way to commit changed files is to run the following commands in a terminal in the FarmData2 development environment.

```bash
git stage <file_1>
...
git stage <file_n>
git commit -m "<your commit message>"
```

Notes:

- Be sure to replace `<file_1> ... <file_n>` with the paths to the files you want to stage and to use a short but meaningful commit message in place of `<your commit message>`.
- Note: the `git stage .` command is a useful shortcut that stages all changed files. Use this only when all changed files are a part of the _named unit of work_ that you are committing.

### Attribution Commit Trailers

If you were assisted by another person or an AI tool in the creation of the content in a commit you must include an commit trailer giving attribution. FarmData2 uses three commit trailers to make different types of attribution. Use your best judgment in selecting the appropriate trailers.

#### Human Coauthors

If you worked with another human on the commit, add a `Co-authored-by` commit trailer when you make your commit as follows.

```bash
git commit -m "<your commit message>" \
  --trailer "Co-authored-by: First Last <first@example.com>"
```

If you had more than one coauthor, add a trailer for each one as follows.

```bash
git commit -m "<your commit message>" \
  --trailer "Co-authored-by: First Last <first@example.com>" \
  --trailer "Co-authored-by: First2 Last2 <first2@example.com>" \
  --trailer "Co-authored-by: First3 Last3 <first3@example.com>"
```

Notes:

- The [Coauthors Generator](https://coauthors.me/generator) utility provides a convenient way to generate a Co-authored-by trailer by using your coauthor's GitHub id.

#### AI Assisted Content

If the commit contains a combination of code created by you and by AI, add an `Assisted-by` trailer when you make your commit as follows.

```bash
git commit -m "<your commit message>" \
  --trailer "Assisted-by: Model, version"
```

Notes:

- Be sure to review the [AI_POLICY.md](../../../AI_POLICY.md) document before making a commit that is assisted by AI.
- Examples:
  - `Assisted-by: GPT, 4.5`
  - `Assisted-by: Claude, 3.7 Sonnet`
- This trailer is generally used when you ask AI to generate full functions or blocks of code, but then add code of your own, or edit and adapt the generated code.
- This trailer is generally not necessary when you use AI autocomplete (_tab completion_) for fragments of code, under the assumption that you will review each of the AI suggestions carefully.

#### Human Coauthors and AI Assisted Content

If you were assisted by both a human coauthor and an AI tool, add both a `Co-authored-by` and an `Assisted-by` trailer when you make your commit as follows.

```bash
git commit -m "<your commit message>" \
  --trailer "Co-authored-by: First Name <first@example.com>" \
  --trailer "Assisted-by: Model, version"
```

#### AI Generated Content

If the commit contains only code generated by AI, add a `Generated-by` trailer when you make your commit as follows.

```bash
git commit -m "<your commit message>" \
  --trailer "Generated-by: Model, version"
```

Notes:

- Be sure to review the [AI_POLICY.md](../../../AI_POLICY.md) document before making a commit that is generated by AI.
- This trailer is required when you use a _planning mode_ and _AI agents_ to autonomously generate significant amounts of code. Extensive prompting or collaboration with the AI in the creation of a plan does not change the necessity of a `Generated-by` trailer.
- If you plan to use an AI to generate significant amounts of code that you plan to edit and adapt, use separate commits for the generated code (with a `Generated-by` trailer) and your own modifications.
- A `Generated-by` trailer is, by definition, incompatible with both the `Co-authored-by` and the `Assisted-by` trailers, and should never be combined with them.

#### Adding a Forgotten Attribution

If you forget to add an attribution commit trailer for a coauthor or to acknowledge AI use, you can add one using an empty commit as follows:

```bash
git commit --allow-empty \
  -m "adding trailers`
  --trailer "Co-authored-by: First Name <first@example.com>"
```

Note that pull requests in FarmData2 are [squash merged](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/about-pull-request-merges#squash-and-merge-your-commits), and coauthors or AI attributions added in this way will appear in the squash merge commit along with any others.

### Pre-Commit Checks

When you make your commit, a <!-- vale alex.ProfanityUnlikely = NO : hook is standard terminology here. -->Git _pre-commit hook_<!-- vale alex.ProfanityUnlikely = NO --> will perform a set of checks on the files that you are committing.

These checks include things such as:

- Checking code for:
  - Proper formatting
  - Spelling errors
  - Linting issues (common coding or stylistic mistakes)
  - Correctness (new and existing tests for staged files must pass)
- Checking documentation for:
  - Spelling errors
  - Broken links
  - Use of inclusive language

<!-- vale alex.ProfanityUnlikely = NO : failure refers to an automated test not a person here. -->

If any of the pre-commit checks fail, the reasons for the failure will be displayed and the commit will not be made.

If a commit fails due to the pre-commit checks you will need to:

- Address the reason for the failure.
- Stage any files that you modified in addressing the failure.
- Try the commit again.

### Next Steps

If the issue you are addressing is not yet finished you should:

1. [merge upstream changes into your feature branch](./8.md) to reduce future merge conflicts.
2. [Push your feature branch to your fork](./9.md).
3. [Create a draft pull request](10.md), if you have not already.
4. Loop back to [make and test more changes](./6.md).
